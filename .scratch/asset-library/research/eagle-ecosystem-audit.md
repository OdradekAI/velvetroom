**已确认生态范围整体合理，主要缺口在 37 和 38 的具体产品契约。** 小型插件中心、精选资源与自有素材包确实能支撑 Eagle 式产品形态；只做入口或展示目录，尚不足以兑现 35 的“真正可用”。必须先选出插件解决的任务、首批内容来源、包往返应保留的数据，再完成工作台场景和隔离运行验证。

## 2. 35 — Eagle 产品形态与扩展生态的首发边界

**现状：已确认，建议保留。** 用户选择的是自有插件、自有资源包、小型精选中心、已有个人图库不依赖目录服务；这与复刻主要交互形态不冲突。

官方把插件与资源分列。插件目录包含功能分类、价格类型、搜索和排序；资源目录另有灵感／素材、版权、仅 eaglepack 等筛选。[插件目录](https://community-en.eagle.cool/plugins)、[资源目录](https://community-en.eagle.cool/resources)

官方文档把窗口、后台服务、格式扩展、检查器列为四种插件形态：一次操作、常驻任务、缩略图／预览扩展、右侧上下文信息分别承担不同作用。[插件类型](https://developer.eagle.cool/plugin-api/get-started/plugin-types)

**合理性评估：**“中心存在”不要求首发实现四种扩展形态或公共投稿。已确认自有契约、不兼容 `.eagleplugin`／整套 Eagle API，可避免把竞品的运行时和第三方原生依赖隐含带入 Tauri。`.eaglepack` 兼容后置与“不迁移图库”也已分别回答，不应重新混问。

**仍需交下游明确：**两个中心在桌面中的固定入口、已安装管理与在线发现的关系、选中素材的快捷调用、离线失败反馈、可供使用的具体插件／资源。Eagle 的 AI Action、AI Search、MCP 等入口可以作为后续演进参考，但不改变当前 Agent／模型后置、未来使用 opi 的决定。

**工作台场景：**从素材列表调用一个已安装插件；从中心看详情并回到原选择；离线进入“已安装”仍能使用本地能力；目录服务故障不遮蔽个人图库。35 不必重开，36 应以这些具体场景验证形态。

## 3. 37 — 首发插件能力、权限与生命周期

### 3.1 首批插件必须先有实际用途

**现状：开放且可开始，不能由“Eagle 有哪些插件”直接得到本产品清单。** 本轮核对了四个由 Eagle App 发布的具体样例，便于围绕创作者任务选择：

| Eagle 官方样例 | 可证实的产品形态 | 对本产品的候选价值及取舍 |
| --- | --- | --- |
| [Media Info](https://community-en.eagle.cool/plugin/media-info) | 右侧检查器显示音视频编码、帧率、时长、码率等 | 适合挑选可用于剪辑的素材；本产品基础预览必需的信息仍应由核心提供，插件只补充更深属性。不能把能显示编码当作能解码播放。 |
| [Exif Metadata](https://community-en.eagle.cool/plugin/exif-metadata) | 右侧查看拍摄参数和地理信息；当前说明含地图入口 | 适合摄影素材筛选；可先选只读本地字段，地图／外部服务须另定是否需要。不能因为原文件存在 GPS 就自动外发。 |

上述是官方产品功能描述，不是源码审核、性能或跨平台实测。详情中的实现工具不能成为本产品自动选型。

**建议供选择：**先比较“媒体属性检查＋图片比较”等少量本地只读插件，与“必须首发提供一个生成成果的工具”两种路线。前者较符合已确定的素材管理／外部创作边界；后者需要明确哪项创作能力、成果保存与许可依赖。不要为了验证写接口而人为添加没有用户价值的写插件。

**需要用户回答的真正缺口：**首发用户会反复使用哪两三个插件？分别从右侧检查器、素材右键／快捷键还是插件独立窗口进入？是否只由产品团队提供维护？是否允许普通用户从磁盘安装团队发布的离线插件包？这几项不能从 Eagle 官方资料替用户决定。

### 3.3 安装、更新、禁用和卸载

| 阶段 | 可用的官方事实 | 本产品还缺的具体答案 |
| --- | --- | --- |

**优先采访顺序建议：**先定用途及提供者，再定安装来源和必要能力，最后用一个“运行中点更新／禁用／卸载”的场景收束生命周期。避免先问几十项抽象权限，再发现首批插件全部只读。

**本机只读核对清单（交主代理）：**插件面板／菜单／中心的相互跳转，详情字段，已安装与待更新状态；如没有已安装样本，禁用入口只能保留官方文档级证据，不为核对而安装或运行未知插件。

## 4. 38 — 精选资源与素材包交换的产品契约

### 4.1 精选资源取得的产品闭环

资源中心的“发现”与“取得”必须区分。官方 `3d-icons` 详情同时给出来源网站与包下载，并显示类型、版权、分类和更新时间；本轮本地另一详情还显示文件数与容量。一个资源页可以有外部来源链接，但链接存在不表示本产品已取得媒体或获得分发权。[详情示例](https://community-en.eagle.cool/resource/3d-icons)

Eagle 社区条款包含教育用途／商业用途分类，同时限制以其站点内容作为竞争素材管理产品的素材来源及自动批量下载。因此沿用35“自己整理且有相应权限”的内容来源合理；此处只记录所读条款，不替任何具体资源作授权结论。[社区条款](https://community-en.eagle.cool/terms)

**可评审的首发流程建议（未采纳）：**分类／搜索 → 详情（预览、发布者、原始来源、许可说明、包版本、文件集合和大小）→ 选择取得目标／整理目标 → 准备与下载 → 校验 → 导入结果 → 查看新条目。失败反馈须区分目录不可达、文件未取得、包不完整、下载完成但入库未完成，不把一个“下载完成”提示当作全流程成功。

**需用户裁定的缺口：**

1. **首批内容与责任人**：究竟提供摄影／纹理／透明 PNG／短视频／音效中的哪些，谁准备并维护来源与授权记录？至少要有可发布的真实资源清单；测试夹具与空目录不替代首发内容。
2. **来源与取得方式**：首批是否只包含可由团队直接分发的完整文件／自有包？如果还收录仅跳往原网站的灵感链接，界面必须明确“查看来源”，不能承诺一键下载任意站点。
3. **目录离线体验**：是否保留上次目录和详情、如何显示刷新时间？已有取得内容可继续用；首次离线无目录如何引导？不能让目录故障阻塞本地图库。
4. **资源更新**：同资源新版本是另一次导入、新建条目还是用户选择补充？已编辑标题、标签、注释不能被远端更新默认覆盖。旧下载版本及当时许可说明怎样查看，需明确。
5. **保存位置**：取得到本机、移动盘或 NAS 是否统一走导入目标？应用管理的暂存包、已入库原件和用户主动保留的下载包是不同对象，取消与清理不能互相冒充。

这些是38已有问题需要落成答案的部分，不建议再造一个泛化“市场”决策。具体下载协议／服务部署放14／13；目录运营并不自动等于云端个人图库。

### 4.2 素材包的核心产品事实与未决矩阵

官方说明 `.eaglepack` 是专有格式，记录分类、标签、标题、URL、标注、备注等；可双击并确认导入，或拖入 app。[打开素材包](https://community-en.eagle.cool/how-to-open-eaglepack-file)

导入／导出帮助进一步明确：标签可保留但不包含标签组；以文件夹导出时保留类别层级；从素材／文件夹右键导出，再选文件名和输出路径。官方也提及它可用于部分素材备份，但这不等于整库恢复保证。本产品已确认“包不替代图库备份”，建议保留。[导入／导出正文](https://en.eagle.cool/support/article/import-exporting-eaglepacks)

官方“不完整导入”排查指出空间不足、包损坏／缺文件是实际问题，并建议对包副本检查 `pack.json`、素材目录及原文件／缩略图／元数据。它提供故障排查事实，**没有完整公开跨版本交换规范**；不能由“能当 zip 查看”推断本产品兼容或完整保真。[不完整导入排查](https://cn.eagle.cool/support/article/troubleshooting-incomplete-library-pack-imports)

本产品需要以下字段／关系矩阵。右栏均为需要选择的缺口，不是已确认实现：

| 对象 | 已确认基础 | 需要38明确的产品结果 |
| --- | --- | --- |
| 原文件 | 不修改原件；可导出独立包 | 全部原字节及已承诺附属内容怎样纳入；完整包才发布还是允许明确的不完整包；离线／缺失项是否阻断、跳过或另选子集 |
| 条目身份 | 条目与文件字节不是同一身份 | 同库回导、异库导入、新版本包各如何判重；不能直接用内容 hash 合并个人整理记录 |
| 多条目共用原件 | 可有独立条目共享实际原件 | 包内保留多个条目时，导入后是否继续共用一个物理文件；既不丢条目，也不能把多归属误写成多个副本 |
| 文件夹与多归属 | 逻辑树及多归属已确认 | 导出一个子树时保留哪些归属；树外归属不应无提示扩张包范围；多个选中根及同名目录如何展示 |
| 标签／评分／注释／标题 | 属用户管理记录 | 哪些默认携带、哪些可关闭；来源方字段与接收方已有字段冲突时如何预览；标签组没有首发已选依据 |
| 资料—媒体关系 | 20有独立资料、媒体、有序关联 | 选媒体时是否连同关联资料；选资料时是否含全部关联媒体；包外引用如何表现，缺失关系不能静默消失 |
| 来源／作者／许可 | 资源详情与收集来源是独立于个人注释的信息 | 保存目录版本及来源声明，是否携带许可文本／引用；个人修改不应被当成资源原始授权声明 |
| 时间 | 首次加入、用户修改、源时间等已分开 | 接收方本次加入时间与来源库时间分开保存；不能将源库加入时间伪装成本库首次加入 |
| 智能文件夹 | 查询规则仍待08裁定 | 导出当时结果、规则还是两者；规则引用包外标签／文件夹怎样处理。不能让“导出文件夹”暗含完整查询系统迁移 |
| 缩略图／代理／离线保留／工作文件 | 内容角色与保护不同 | 默认包是否只含原件和管理信息；不能把缓存或工作文件直接当作分享原件；是否携带派生预览需用途和体积依据 |
| 插件设置／可执行内容 | 插件包是独立安装对象 | 资源包不能因含脚本或配置而自动安装／运行插件；应用设置、凭据不应隐含进入素材分享范围 |

**包之间的关系建议：**收集包负责接收外部资料与文件，分享资源包负责导出已整理的选定内容；二者应共用已经选择的资料／媒体／来源／关系语义和导入规则。可有不同产品入口或导出预设，是否一个封装格式由14决定。不能为了名字不同再造一套素材身份、时间或重复判断，也不能用“复用收集包”略过分享隐私预览与多归属保真。

**导出隐私预览应有具体样例：**选一个文件夹，其中一张图还在私人文件夹中、有个人注释和本机路径。预览应能明确哪些内容进入包、哪些仅留在本机；用户不应靠读规范猜测。源路径、目录外关系、笔记和来源链接各自怎样默认选择，须通过38裁定，不能只显示“包含元数据”。

## 5. 39 — 插件运行、权限与生命周期的验证原型

**现状：开放，前置14／37合理。** 建议先在36展示用途和完整操作，再以39验证所选机制；不必为了还没选择的后台服务或写权限搭建通用插件沙箱。

原型至少验证一个真实有用的首批插件：安装后能在约定入口出现并完成业务；无选择／不支持格式／原件离线得到正确反馈；切换选择不会把旧结果贴到新素材；禁用不再接受新调用，卸载不删除用户素材／成果；更新失败与不兼容包有实际结果。若首发只读，就验证拒绝越界读取／未开放写能力，不凭空增加处理成果功能。

“权限拒绝”的状态演示只能证明用户理解；真正的未授权调用计数和文件变化由隔离样本证明。Eagle 审查条款和自有插件发布者承诺均不能代替本产品真实验证。原型若实现不了已选契约，回修14或37；不能用一句“参考 Eagle”关闭39。

## 6. 40 — 资源取得与素材包交换的验证原型

**现状：开放，前置05／14／38合理。** 关键不仅是下载或成功解包，而是把取得、入库和选定字段保真连接成可复现实验。

建议最小自建样本包含：一个资料关联三张媒体且顺序明确；其中两条记录共用一个原件；两级文件夹、一项多归属、中文标签／注释、来源与授权声明；另有一个明确缺失文件的失败包。只在38确定这些保真承诺后形成验收期望。

真实实验分开记录：下载成功／校验成功／已提交条目，导出期间原件变化，中断后重试，不支持版本，路径越界包，已存在目标，同库回导和异库回导。比对的是最终文件、字段、关系与任务结果，不能仅比较素材数或包大小。

测试服务只提供受控故障与数据，不能替代真实首发目录维护和内容分发责任。Eagle 资源包兼容已经后置，不应成为此原型的阻塞，也不能下载 Eagle 社区包充当本产品种子内容。

## 7. 14 — Rust 核心与界面的深模块划分

**现状：开放，尚不能采纳模块清单。** 票已明确使用 codebase-design、先有产品行为再定 Interface，方向合理。Eagle 四类插件是扩展产品形态，既不是本产品四个 Module，也不证明应采用 Node／Electron／某个包封装。

当前需保持的责任边界：

- **业务权威**：UI、插件、未来 Agent 共享 Rust 领域行为和来源标记；插件状态、资源取得任务、素材原件和管理记录不能由不同调用方各自维护一套互相冲突的真相。
- **内容入口**：目录资源、离线收集包、用户分享包可有不同 provenance，但进入相同已确定的身份／导入／取消规则。
- **代码入口**：插件安装／更新与素材入库是不同事务；资源包不自动变成插件安装包。运行状态与业务任务状态也不能用一个“已关闭”合并。
- **本机能力**：已选择多卷、挂载 NAS 和本地工作文件，路径访问知识须集中；未来 C/S 不能假定服务器能直接读取用户外接盘。
- **opi**：使用 OdradekAI/opi 是已确认未来约束；嵌入方式、版本、工具桥仍未选。既有研究已指出 abort、会话恢复与业务任务收束不同；本轮不重做其事实调查、不提前实现 Agent。[opi 研究](opi-integration-evidence.md)

需要澄清的文档边界：14要求说明后续 Agent 和 C/S 的职责映射是合理的，但首版 spec 不应因此必须选择完整云协议、模型供应商或运行一个 opi 进程。首发应验证自己实际使用的界面／插件业务接口；未来部分明确“复用哪些契约、新增哪些能力、哪些未决定”。

## 8. 15 — 前端与持久化技术候选的采纳条件

**现状：开放，候选／已定没有发现混写，建议继续保持。**

| 项目 | 正确记录方式 | 不能据此宣称 |
| --- | --- | --- |
| Rust 核心 | 用户已确认 | 具体 crate、任务存储与模块已选 |
| Tauri + Web | 用户接受的路线 | React 必须采用、插件拥有 Node、Eagle API 兼容或双平台媒体已通过 |
| React + TypeScript + Vite | 待采纳候选 | 已成生产界面栈 |
| SQLite + rusqlite | 首版本地持久化候选 | 文件动作与数据库天然原子、中文搜索已满足、未来服务器也必须采用 |
| OdradekAI/opi | 后续 Agent 指定技术约束 | 首发 Agent 已纳入、实际嵌入方式／版本已定、其 package 等于产品插件中心 |

本轮未调查 React、SQLite 或其他组件的新 API，不作采纳建议。15需把每个候选与具体界面负载／查询／恢复结果关联；“Eagle 能做到”不是候选可行性的证据。

## 9. 16 — 首版取舍闭合与规格交接条件

**现状：继续开放合理。** 生态部分尚不够交给新会话直接实施，原因可具体列为：

1. 37没有首批插件用途、调用入口、必要能力和版本／生命周期矩阵。
2. 38没有真实内容清单和维护责任，也没有资源包字段／关系往返矩阵。
3. 36尚未把这些功能与素材列表、详情、任务反馈连成用户走得通的工作台。
4. 39／40尚未有真实运行和异常证据；目录页面、状态模拟不能代替它们。
5. 14／15的候选仍待产品契约和实测输入；26的局部 macOS 实验也不能替代 Windows／发行验收。

建议将最终 spec 的生态验收按“一个用户任务 → 输入与可见入口 → 成功结果 → 中断／冲突 → 维护或分发依赖 → 证据”写完整。继承35范围即可，不重复询问已回答的 Eagle 兼容或 Agent 后置。若发现新取舍，先给用户具体场景和推荐；本报告不自行将它们后置。

## 11. 工作台原型应具备的可操作场景

以下是供36和专门原型选择的场景清单，不是本轮已实现功能，也不是要求用户一次回答全部问题：

| 场景 | 需要在界面中明确的状态／选择 | 最终证据归属 |
| --- | --- | --- |
| 从素材列表比较两张图片 | 原选择、输入范围、离线项、关闭工具后回到原位置 | 37先定用途；36体验，39真实运行 |
| 检查器显示视频详细参数 | 加载、无此字段、不支持、源离线、切换选中素材后旧结果取消／失效 | 37／22；36与39 |
| 中心安装一个团队插件 | 详情、发布者、兼容、能力、准备、已安装与已启用分开 | 37；39 |
| 运行中更新或禁用 | 等待任务收束、取消请求、结果待核验，不能直接显示完成 | 37／14；39 |
| 卸载含设置／缓存的插件 | 明确将移除什么、保留什么；素材和成果保持存在 | 37／06；39 |
| 断网进入插件／资源中心 | 已安装能力、上次目录、不可取得的新内容各有状态 | 35／37／38；36 |
| 取得一个精选素材包 | 查看来源及许可、集合与大小、选存储与分类、下载、校验、导入结果 | 38／05；40 |

| 分享一个多归属文件夹 | 包范围、树外关系、注释／路径等隐私预览、缺失原件提示 | 38／04／22；40 |
